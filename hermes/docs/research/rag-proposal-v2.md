# BlastGame RAG 建法方案 v2（历史提案）

> **已被当前实现取代。** 本文保留 2026-08 的方案演进；其中增量索引、25 条 QA 和模型对比并非现行实现或实测结论。现行行为与指标见 `../../rag/README.md`、`../../rag/index/build_manifest.json` 和 `../../rag/index/evaluation.json`。
> 当时目标：形成可验证的本地检索方案，并记录关键技术取舍。

## 数据源（当时方案）

| 数据源 | 做/不做 | 理由 |
|--------|---------|------|
| **游戏系统/模块说明文档**（用户新增） | ✅ **做** | 叙述性知识，语义检索主场；低频、帮理解——正是 RAG 该管的 |
| wrongbook.md（踩坑教训） | ✅ 做 | 叙述性，语义检索价值大 |
| .hermes.md 规则精华 | ✅ 做 | 描述性知识 |
| review/phase 结论（蒸馏后） | ⚠️ 可选 | 只索引"规则+一句话 rationale" |
| board.md / timeline.md / 池子 / 规则 | ❌ 硬禁 | 结构化精确数据，RAG 引入噪声+stale |
| memories/ 过期快照 | ❌ **必须排除** | 毒源，绝不能索引 |

**核心洞察**：和调优不直接相关、但可能用到的**游戏模块文档**，恰恰是 RAG 最适合的（低频+帮助理解）。高频硬规则仍走 .hermes.md/skill。

## 技术栈（本地，零平台依赖）

- Embedding：`BGE-small-zh-v1.5`（中文好、轻量；**检索必须加 query instruction**）
- 向量库：`FAISS` + `IndexFlatIP`（**L2 归一化后内积 = 余弦**，BGE 官方要求 cosine）
- Chunk：**语义切分**（一条笔记=一个 chunk，超长才二次切），不做固定 512+按字换算
- 检索：当时提议内容 hash 增量索引；现行实现为安全扫描后全量重建并原子替换
- 集成：做成本地 CLI 命令

## 时间防线（修正版：内容 hash + 增量重索引）

**错误版本**：源文件改了没重算 → return empty（会讲不通：召回率归零）
**正确语义**：
1. **内容 hash（blake2b/md5）检测变化**，不用 mtime（会误报）
2. 查询前遍历索引清单，发现 hash 变了 → **只重索引该文件**（增量更新对应 chunk）
3. **口径统一（P1）**：小语料下"单文件局部更新 FAISS"不划算——落地做法是 **hash 级跳过未变文件 + 变化文件全量重建索引再原子 swap**，既保证一致又简单。叙事上弱化"单文件增量"，强调"hash 级跳过未变文件"
4. 元数据存 **sidecar**（源文件/chunk文本/hash/时间戳），不塞进向量 float 数组；**sidecar 冗余存 chunk 文本是为了源文件被删后仍可追踪**（会被问"为什么冗余"，要能答出用途）

**当时设想**：用内容 hash 管理索引一致性；该增量方案未落地，不能视为现行能力。

## 数据源边界（P2 补充）

- **模块说明文档定位为"理解型"**：用于回答"这个模块是干什么的、机制怎么运作"，**不回答精确数值问题**（如"伤害具体是多少"）
- 原因：模块文档里的精确数值可能过期（改版后变化），RAG 检索到旧数值会误导
- 工程边界：模块文档定位理解型，精确数值走结构化真源，不靠 RAG

## 语义切分边界（P2 补充）

- 语义切分适合**笔记/规则语料**（一条笔记=一个 chunk，契合语义单元）
- **超长笔记（>512 token，BGE 上限）的二次切分规则要明确**：按段落/句子自然边界切，不硬切
- 工程边界：短笔记按语义单元切分，长文档需按自然边界继续拆分

## 评估体系（最大软肋，P0 必须优先）

- 手工造 **20~30 条 golden QA**：从原文改写成不同措辞，标注正确答案指向哪条原文
- **QA 必须覆盖三类源**：wrongbook / 模块说明文档 / 规则（否则评估对新增源失效）
- 评估脚本跑四指标：**Top-1 hit rate、Recall@3、Recall@5、MRR**
- **消融表**逐项实验，不拍脑袋：
  - chunk_size ∈ {语义切分, 256, 512}
  - overlap ∈ {10%, 20%, 30%}
  - Top-K ∈ {3, 5, 10}
  - embedding ∈ {bge-small-zh, bge-base-zh, gte-zh}（m3e 已被取代，不作对比项）
- 阈值用 MRR 曲线标定，不写死 0.4
- **MVP 顺序：先建 golden QA + 评估 harness，再调参**（否则选型是自嗨）
- 本节数字均为当时实验计划，不是结果；真实指标只看当前 evaluation.json

## 生成层评估（P1 补充）

- 检索层评估（hit rate/recall/MRR）只测"检得对不对"，不测"答得好不好"
- 如实划界：**本 MVP 聚焦检索层评估**，生成层（回答质量）不属于本次范围
- 后续候选：增加 LLM-as-judge 或人工评分评估生成质量；当前尚未实现

## 当时记录的技术取舍

- BGE query instruction：检索不对称时给 query 加指令前缀。
- FAISS 相似度：向量 L2 归一化后使用 IndexFlatIP。
- 切块：优先保留语义单元，而不是固定字符数硬切。
- 索引一致性：增量方案只是提案；现行采用全量重建、manifest 哈希和原子替换。
- 评估：模型对比数字未形成可核验产物，不作为结论。

## MVP 顺序（修正版）

1. **先建 golden QA（20~30条）+ 评估 harness**（最优先）
2. 建索引 + 查询（BGE query 指令、归一化 + IndexFlatIP）
3. 跑消融表定 chunk/k/阈值/模型
4. 时间防线（内容 hash + 增量重索引）
5. 集成 CLI

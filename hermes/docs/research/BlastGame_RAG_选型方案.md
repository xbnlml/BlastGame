# BlastGame RAG 数据源选型 + 整体方案（基于实测盘点）

> **历史选型方案，已被当前实现取代。** 本文保留早期数据源边界与方案论证；旧语料规模、增量重灌、版本号和评估规模均不是现行能力。当前构建与严格指标只认 `../../rag/README.md`、`../../rag/index/build_manifest.json` 和 `../../rag/index/evaluation.json`。

> 依据：全部候选文档已实测盘点（Doc 全量 ~422KB，加 AgentRules/其他说明 ≈ 450KB）。
> 当时目标：验证“约束 vs 知识”的数据源边界，并形成可运行原型。

---

## 0. 总原则：一句话定边界

**凡"违反了会出错/会出事的"文件 = 约束（normative），必须始终加载，绝不进 RAG；
凡"理解了更好、丢了最多少点上下文"的文件 = 知识（descriptive），进 RAG。**

关键反直觉点：**不是"重要的放 RAG"，而是"一秒钟都不能缺的放上下文，缺了也无妨的才放 RAG"。**
把 AGENTS.md / AgentRules 这种约束文件塞进 RAG，等于把安全规则变成"检索到才生效"——召回一旦失败，agent 就会在无约束状态下乱动仓库，这是不可接受的失效模式。

## 1. 数据源选型结果（三张清单）

### A. 始终加载（宪法层）—— 绝不进 RAG
| 文件 | 大小 | 理由 |
|------|------|------|
| `AGENTS.md` | 4.4KB | 仓库级 agent 规则，约束全量生效 |
| `CLAUDE.md` | 0.6KB | 同上 |

## 2. 边界设计（四条判据，可复用）

判定一个文档进 RAG 还是始终加载，问四个问题：

1. **权威性**：这是"必须遵守的规范" 还是 "帮助理解的可选参考"？违反的成本多高？
   - REPO_SAFETY 违反=出事 → 始终加载。
   - Gameplay_Flow 描述不全=少点上下文 → RAG。
2. **体量**：完整塞进上下文是否可行？始终加载预算建议 ≤30KB / ~10K token。
   - 宪法集合 ~31KB → 可行，始终加载。
   - MainGame 327KB → 远超预算，必须 RAG。
3. **可切块性**：切成 500~800 字片段后语义是否仍成立？
   - 叙述性散文 → 切块无损 → RAG。
   - 精简规则清单（如"永远不要 X"）→ 切块即断章取义 → 始终加载。
4. **过期容忍度**：里面夹带精确数值，若过期会造成什么后果？
   - 纯机制描述，数字过期=答错个旧值，可接受 → RAG（答机制）。
   - 平衡/经济数值，过期=按旧数值做决策 → 单独权威管理（见第 4 节）。

## 3. 规模确认：450KB 语料 RAG 价值成立吗？——**成立，但要精确说清**

- **数量级**：~450KB，中文 UTF-8 约 3 字节/字 → ~15 万字符 ≈ **~100K~150K token**，已超出/逼近单次上下文窗口，**无法全量始终加载**。
- **查询形态**：游戏项目开发天然是**模块化、选择性**的——一次几乎只查一个模块（经济/回放/机器人），极少需要全部 63 个模块同时在场。这正是 RAG 的最佳适用场景。
- **结论**：**RAG 价值成立**。但两点修正：
  1. 有效语料要**去噪**：去掉 migration report、重复的 module-index、导航清单后，真实唯一知识约 **~350KB**。
  2. 450KB 属"中小语料"，**不要过度工程**：嵌入 + BM25 混合 + top-k 即可，此规模不需要重排序 reranker。

## 4. 数值过期风险处理（关键生产正确性点）

MainGame 里的 `Coin_Economy`、`Game_Score`、`POWERUP`、`BI`、`Tools` 及 `LevelDatabase` 都夹带精确数值。策略：

1. **元数据打标**：每个文档加 `precision: exact | narrative` 字段。
   - `exact`（经济/计分/power-up/打点字段/层级表）→ 检索命中时，prompt 强制"只按文档原值引用，并带上该文档的版本/时间戳；未检索到则明说，禁止脑补"。
   - `narrative`（机制/流程/架构）→ 正常回答，允许总结。
2. **权威数值单源化**：若存在规范化数值表（如 LevelDatabase），抽出一份**精简的"权威平衡表"**，小到可始终加载（或随版本固定），RAG 文档只描述机制、不重复数值 → 从根上消除"多个文档数值不一致"。
3. **当时提出的版本化再摄取**：每文档存内容 hash + 更新时间、只重灌变化文件。该增量方案未落地；现行采用安全扫描后的全量重建、manifest 哈希和原子替换。
4. **prompt 兜底**：系统提示写明 "数值类问题必须给出文档出处；查不到就答'未在当前语料中找到该数值'，不得猜测"。

## 5. 当时的整体落地方案

### 5.1 脚手架
- **语料目录约定**：`corpus/` 下按 `knowledge/`（进 RAG）与 `context/`（始终加载，进 .hermes.md / AGENTS.md 引用）分两个目录，用约定而非脚本强制——能讲清、工程能落地。
- **始终加载线**：将 A 清单合并精简为一份 `AGENTS.md`（≤25KB），由 Hermes 的 `.hermes.md` 机制恒定注入。

### 5.2 检索路由（亮点设计）
用根目录 `Bot_MainGame_Doc_Navigation` + `module-index/*` 生成一份**语料清单 manifest**（文档名 + 一句话摘要 + 所在模块），始终加载（<5KB）。它不承载知识，只告诉 agent **"有哪些文档可查、该查哪个"**：
- 好处：避免"agent 不知道该搜什么"——先看 manifest 定位到模块，再针对性检索。
- 价值点：这是 RAG 里"检索路由/query 改写"的工程化落地。

### 5.3 切块与索引
- 叙述类按标题切块（500~800 字，50% 重叠）；数值/表格类按节切块，**保证表格/数值块不跨 chunk 断裂**。
- 检索：**混合检索** = 稠密（中文用 bge-m3 / 多语言 embedding）+ **BM25 关键词**（文档代码/术语密集，关键词召回很关键，几乎零成本）。Top-k 取 5~8。
- 当时判断此规模不需要 reranker；是否增加 reranker 应由当前评估数据决定。

### 5.4 注入与回答
- 命中片段按 `[来源文件 + 版本]` 注入，系统提示强制引用出处。
- prompt 双层：机制问题走 RAG 总结；数值问题走"引用原文+版本"；超纲问题（不在语料）→ 明确拒绝/说明。

## 6. 评估设计（golden QA，覆盖每个数据源 + 每类问题）

**问题类型矩阵（每类都要有）：**
| 类型 | 示例（针对本语料） | 验证点 |
|------|------|------|
| 机制理解 | "Blast_Replay 的回放流程是怎样的？" | 总结正确、不夹带过期数值 |
| 实体定位 | "哪些模块涉及金币经济？" | 召回跨模块关系 |
| 精确数值 | "某 power-up 的倍率是多少？" | **防幻觉**：必须引用原文+版本 |
| 跨模块关联 | "Coin_Economy 如何与 Game_Score 交互？" | 检索到多个模块并串联 |
| 边界/所有权 | "奖励计算归哪个模块管？" | 定位到正确模块 |
| 超纲/负例 | "如何在 BlastGame 里做云存档？"（语料没有） | **应拒绝或明说未找到**，不硬编 |
| 过期测试 | 改掉某文档一个数值 → 问旧问题 | 模型必须采信新值并标注版本 |

**构造方法（按语料规模合理）**：
- **每个文档 ≥2 题**：1 个机制题（从该文档标题/小节生成）+ 1 个数值题（仅对 `exact` 文档）或 1 个授权题（narrative 文档）。
- 再加**跨模块题**（从 manifest 的模块关系生成）与**负例/超纲题**（从项目外领域构造）。
- 当时估计约 210 题；现行 Golden QA 规模与正负例划分只看当前 evaluation.json。

**指标**：
- 检索：`recall@k`（黄金片段是否召回）。
- 回答：LLM-judge 判"正确率 / 忠实度（是否脑补数值）/ 引用是否带出处 / 数值类拒绝率"。

## 7. 当时的方案结论

> **宪法层（AGENTS.md / CLAUDE.md / PROJECT_OVERVIEW + 合并后的 AgentRules ≈ 31KB）始终加载、绝不进 RAG；知识层（MainGame/Bot/Tools/小模块 ≈ 350KB 去噪后）进 RAG，混合检索 + 数值打标 + 版本化；导航清单做检索路由；LevelDatabase 单独定权威数值源；~450KB 对模块化查询成立 RAG 价值，但不过度工程。**

# 轻量级标准保障机制设计（2026-08-17）

> 目标：个人项目 + agent 协作场景下，用最小成本保证标准不漂移、被破坏时能及时发现。
> 约束：无 CI/CD、不引入复杂框架、标准更新频繁（用户经常纠正）、agent 是主要执行者。
> 结论先行：**推荐「候选 A：金样回归套件」+ 配套变更仪式**，单文件、零框架、秒级运行。

## 一、失败模式诊断（基于项目实际事故）

| # | 失败模式 | 实例 | 现有防线为什么拦不住 |
|---|---------|------|---------------------|
| F1 | **门禁静默假通过**：检查函数 try/except 吞异常 → 永远"通过" | W10 探针方向检查（`for t in tiers` 遍历 dict key 字符串 → AttributeError 被吞） | `smoke_test.py` 只查 rc==0（"工具没崩"），不查"违规样例必须被打回"（"标准真的在拦"） |

## 二、候选方案

### 候选 A：金样回归套件（推荐）

一个 `tools/check_standards.py`，三类检查，纯只读、秒级：

1. **规则语义金样（核心）**：把历史用户裁定固化为 fixture，调真实函数断言输出。
   - 判定语义：L152 gap=9.99→接近（near_tolerance=1）、L153 灰色带展示、L197 wr=4.2 必须被过滤、dev=10 贴线必须"继续调优"、三态 result 列权威、接近≠入库
   - 门禁自检：**故意违规的探针方案必须被 W02/W09/W10 打回**（直接命中 F1——W10 类事故只有这种测试能查出）
   - 每个 check 失败 = 标准被破坏，输出"症状→对应裁定案例→期望 vs 实际"
2. **rules.json 自校验**：schema 检查（gap_bands 值域、hard_violations 合法、warden_checks id 唯一且与 warden.py 的 check 函数一一对应、tolerance_pp 顶层位置）
3. **文档漂移扫描**：grep skill/references 中与 rules.json 冲突的硬编码数值（"T3<60"/"20pp"旧值），列"文档说 X / rules.json 说 Y"

触发方式（零 CI）：
- **变更仪式（主）**：每次用户纠正/标准更新 → 改 rules.json → 跑 check_standards.py → 全绿才允许更新 skill/记忆
- **管线绊线（辅）**：auto_loop.py / preflight.py 启动时加 1 行调用——W10 类问题当场爆，不用等用户发现
- **按需**：用户怀疑 / 每周一次

成本：脚本 ~250 行 + 首批 fixture 8-12 条（从 08-17 审查清单和历史裁定抽）；之后每次用户纠正 agent 顺手加 1 条 fixture（约 10 分钟）。
收益：直接消灭 F1（门禁假通过）、F3（裁定不固化）、F2 的代码侧；F4 由绊线解决。

### 候选 B：标准变更协议（纯流程，零代码）

"标准四步"仪式：① 改 rules.json（单一真源）→ ② 跑验证 → ③ 同步 skill/memory/references（已有 knowledge-routing 决策树）→ ④ 记 changelog（rules.json `_meta.updated` + 一行说明）。
优点：零代码零成本。缺点：纯靠 agent 自觉，无机器兜底——**正是当前"靠记忆+文档会漂移"问题的同类**，单独用不可靠。**只作为 A 的配套流程并入，不单独推荐。**

### 候选 C：门禁自检内嵌（warden.py 加 --self-test）

内置违规样例，启动时跑每个 check 函数断言"违规必被拦"。
优点：检测点离门禁最近，每次 warden 调用都顺带自检。
缺点：只覆盖 warden 一个闸门（judge/pool/文档漂移不覆盖）；自检代码与门禁代码同文件，改门禁时可能一起改坏（同源失效）。**A 的"门禁自检"部分已包含此能力且覆盖更广**，不单独选。

## 三、推荐：候选 A，B 作为配套流程并入

理由：
1. **直接命中头号事故**：F1（门禁静默假通过）只有"故意违规必须被打回"的金样能查出——现有 smoke_test.py 查 rc 不查语义，查不出来
2. **把"用户反复纠正"从负担变资产**：标准更新频繁 = fixture 持续增长 = 防线越来越强；每个裁定永久生效，不再怕后续改动推翻
3. **完全符合约束**：单文件、纯标准库、无框架、无 CI、秒级、agent 可执行（只读，不碰 git/asset）
4. **绊线解决"及时发现问题"**：管线入口 1 行调用，成本≈0，收益=W10 类事故不再需要用户发现

## 四、落地清单

1. 新建 `tools/check_standards.py`（三类检查：金样回归 / rules.json schema / 文档漂移扫描）
2. 首批 fixture：从 08-17 审查清单 + 历史裁定抽 8-12 条（L152/L153/L176/L197/L200/W10 方向检查故意违规样例）
3. skill 加「标准变更四步」小节（改 rules.json → 跑 check_standards → 同步文档 → changelog）
4. auto_loop.py / preflight.py 启动加 1 行调用（可选，先手动跑也行）
5. 铁则：**每次用户纠正标准 → agent 必须加对应 fixture 才能算完成**（否则回到 F3）

## 五、验证方式

- 用 2026-08-17 审查清单的"实测违规样例能被打回"方法：故意构造 W10 违规探针 + L152 边界判定，check_standards 必须报 FAIL
- 破坏性测试：临时把 rules.json 的 t3_min 改回 60 → 文档漂移扫描必须报"文档/rules 不一致"（对照 skill 中"已下调 50"的记录）

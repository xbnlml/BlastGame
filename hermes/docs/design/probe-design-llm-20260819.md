## 0. 一句话方案

**探针设计由 LLM 主导（每轮每关参与），规则只做安全闸门（拦违规不拦差异），回测数据只做裁判（反馈优化 LLM 方式，绝不因效果暂时不好就退回纯脚本）。** 全程记录设计理由与流程，用户要看时展示。

---

## 1. 背景与用户裁定（为什么这样做）

### 1.1 用户裁定（2026-08-19 原话要点）
1. **探针设计无法真正脚本化**：每关情况不一样，参数↔胜率关系非单调（L136 高 sd 反而是容易区），达到目标胜率需要综合分析（池子、历史、关卡特殊性），目标缺口胜率也要根据现有情况判断，不能一味贴近目标。
2. **缺口分析 + 参数设计两者都不能纯靠脚本**；探针每轮都要跑新的，绝大多数意味着要 AI 参与设计。
3. **全自动调优时没有用户和主 agent 参与**——无人值守时探针设计完全靠脚本，没有任何智能判断。
4. **方向已拍板**：即使回测发现 LLM 设计的探针命中率暂时不如脚本，**也是优化 LLM 的方式方法（输入/铁则/prompt），不退回纯脚本**——这条路是对的。
5. **非 verified 数据有参考价值**：胜率不精准，但分析参数如何影响胜率的**大趋势**没问题，必须作为 LLM 输入。
6. **探针设计理由与整个流程都要记录**，用户要看时再展示（不主动推送）。

### 1.2 评审结论要点（沿用）
- 评审 agent 验证：`agents/*/memory.md` 无消费者（唯一读写方是 curator 自己、输出被吞）——**一切"写进 memory 反思区"的产出都是浪费**，改为写 advisor 文件/批次简报，消费方是用户。
- 评审 agent 确认保留：**批次综合参谋**（每批 1 次 LLM：简报 + 卡壳换思路 + 规则空白建议）、**卡壳第二意见**（连续 ≥2 轮无进展的关，LLM 读轨迹给替代方向）。
- 评审 agent 砍掉的（同意）：Curator 统计→解读、离线 A/B 合成回放、Judge LLM 边界推荐（改确定性边界报告）、W10 改法建议（warn 已含方向）、记忆反思区、每 agent 各问一条的仪式反思、每轮 5 次配额框架。

## 2. 架构总览（三层）

```
第 1 层：LLM 探针设计器（每关每轮 1 次调用）——核心新增
   ↓ 输入分层（见 §3.2）│ 输出：目标段 + 5 槽配置 + 理由（见 §3.3）
第 2 层：规则安全闸门（确定性，复用/抽取现有 Warden 铁则）
   ↓ 只拦"违规"（5槽全用/sd跨度/ratios多样/非已验证配置/Warden）
   ↓ 不合格 → 打回 LLM 重设计 1 次 → 仍不合格 → 脚本方案兜底（保证有探针可跑）
第 3 层：回测 + 批次综合参谋（数据裁判 + 简报）
   ↓ probe_hitrate.json 记每槽实际 WR vs 目标段 → 数据积累
   ↓ 命中率低 → 优化 LLM 方式（输入/铁则/prompt），不退回脚本
   ↓ 批次结束 → 综合参谋（简报/卡壳建议/规则空白）→ 给人看
全程：设计理由 + 流程 → project-state/advisor/ 文件，用户要看时展示
```

**核心变化**：LLM 从"参谋"升级为"探针设计核心参与者"；脚本从"设计者"降级为"安全网 + 参考 + 兜底"。规则校验**不要求 LLM 输出与脚本一致**——只要不违反铁则，LLM 方案与脚本不同也应被接受。

## 3. 核心设计：LLM 探针设计器

### 3.1 落点与调用方式
- 新增 `tools/design_probes_llm.py`，替代（或旁路）现有 `design_probes.py` 的设计主体。
- 调用点：`auto_loop` 每轮每关设计探针处（现状走 `planner → agent_analyze → design_probes`），替换为 `design_probes_llm`。
- 每关每轮 **1 次 LLM 调用**（这是核心投入，不可避免；相比跑 400 局 bot 是零头）。
- 复用 `tools/llm_client.py`（若已建）或新建极简封装：唯一 LLM 入口，失败返回 None 不抛异常，usage 记账。

### 3.2 LLM 输入（分层，必含非 verified）
```
1. verified 数据（精准状态）：当前各档 WR、缺口(gaps)、判定 reasons
2. 全量池子数据（含非 verified，趋势参考）：参数(sd/sc/ratios/of)↔胜率分布、WR 范围
3. 目标胜率（Excel 真源 lv_win_config_test.xlsx 对应关）
4. 历史探针与结果（本关近几轮：探过什么配置、实际跑出什么 WR）
5. 铁则（踩坑经验清单，LLM 不得违反，见 §4.1）
6. 脚本候选方案（现有 design_probes 输出，作为"参考答案"——LLM 可采纳/改进/换思路）
```
> 输入只传结构化摘要，绝不全量池子灌入（成本控制）。

### 3.3 LLM 输出（结构化 JSON）
```json
{
  "target_tiers": ["T1", "T3", "T5"],
  "probes": [
    {"tier": 1, "sd": 15, "sc": 5, "ratios": "1,1,1,1,1", "of": 0.4,
     "rationale": "T1 离目标 80% 差 12pp，历史 sd15-20 区间 WR 普遍偏高，取低 sd 拉高"},
    {"tier": 3, "sd": 30, "sc": 5, "ratios": "10,1,1,1,1", "of": 0.5,
     "rationale": "T3 目标 60%，当前 58% 接近，用前段重 ratios 试探是否偏高可压"},
    ...
  ],
  "design_note": "本关 T1-T3 缺口不足，优先拉开；T4 已达标不动"
}
```
- 每槽必须含 `rationale`（设计理由）——这是"AI 参与"的证据，也是用户查看时的展示内容。
- 输出 schema 校验（JSON 模式 + 字段白名单 + 数值范围），非法即弃、重设计。

### 3.4 prompt 要点（执行时打磨）
- 角色：资深游戏难度调优专家，熟悉该关卡历史。
- 明确告知：参数↔胜率非单调，要结合池子趋势 + 历史探针判断，不要套固定模板。
- 明确告知：目标缺口要"根据现有情况判断"，某档已验证离目标极远时优先修能修的，不一味贴目标。
- 铁则作为"硬约束"列出，违反即重设计。
- 要求输出 ≤ 一定字数，控 token。

## 4. 规则安全闸门

### 4.1 校验项（确定性，复用现有 Warden/铁则）
| 校验 | 规则 | 来源 |
|------|------|------|
| 槽数 | 5 槽全用，不留空 | 探针铁则 |
| sd 跨度 | 档位间 sd 有实质差距（大跨度探边界，禁止 1-3pp 窄步长） | 探针铁则 |
| ratios 多样 | 有实质差异（前段重/后段重/均匀），禁止 10,1,1,1,1 与 10,1,2,1,1 这类本质相同 | 探针铁则 |
| 四元组唯一 | 不与已验证/已探过配置重复（防 Unity dedup 吃掉） | W02/W09 |
| 方向合理性 | 目标段方向（缺口档 sd 偏难/偏易警告） | W10 |
| 配置有效性 | sd/sc/ratios/of 数量匹配、数值范围合法 | validate_tiers |

### 4.2 打回逻辑
- LLM 输出违反铁则 → **打回重设计 1 次**（附上具体违规项，让 LLM 修正）。
- 打回后仍不合格 → **回退脚本方案**（现有 design_probes 输出），保证有探针可跑。
- 打回/回退全程记录到 advisor 文件（用户可查"为什么这次用了脚本方案"）。

## 5. 回测 + 批次综合参谋（数据裁判）

### 5.1 探针回测记账（纯脚本）
- 新建 `project-state/probe_hitrate.json`：每轮批跑后回填每槽探针实际 WR vs 目标段。
- 指标：探针命中率（实际 WR ∈ 目标±5 的槽占比）、单轮修好率（不合格→合格/接近）、有效信息率（新增非重复数据点）。
- **不依赖 LLM**，是探针质量真实数据，也是卡壳触发与"优化 LLM 方向"的依据。

### 5.2 批次综合参谋（每批 1 次 LLM，评审 agent 设计保留）
批次结束（auto_loop 完成/停止）触发，LLM 一次性读：全批 round report + probe_hitrate + 黑名单 + 边界报告 + 用户改裁日志。产出三样，全部有消费者：
- **A. 给用户的批次简报**（≤150 字）：哪些关待确认入库、哪些待确认改关卡、哪些边界案例需要看、哪些关卡壳。
- **B. 卡壳关换思路建议**（仅当卡壳触发命中，≤150 字/关）：连续 ≥2 轮无进展的关，LLM 读轨迹给替代方向。采纳后走既有 Warden 闸门 + 下一轮验证。
- **C. 规则空白建议**（仅当用户改裁或边界反复出现）：建议新增/修改一条规则。消费方：主 agent → 用户确认 → 才改 rules.json。

### 5.3 优化循环（用户的裁定）
- 若回测显示 LLM 探针命中率暂时低于脚本：**优化 LLM 方式方法**——调整输入（加更多趋势数据）、调整铁则/倾向描述、打磨 prompt、加 few-shot 示例。**绝不退回纯脚本。**
- 每 N 批或人工触发时做一次"LLM 探针质量复盘"，产出改进建议给人确认。

## 6. 记录与展示（用户要看时展示）

- 每次探针设计全程记录：输入摘要、LLM 输出（含 rationale）、闸门结果（过/打回/回退）、最终方案。
- 落盘 `project-state/advisor/probe_<lv>_<round>_<ts>.json`，只追加不覆盖。
- **不主动推送**；用户要看时，主 agent 读 advisor 文件按关展示：目标段选择理由 + 每槽设计理由 + 闸门结果。
- 批次综合参谋的简报是**唯一主动推送**的 LLM 产出（批次结束给用户）。

## 7. 落地步骤（每步独立可交付、可回退）

### Step 1：LLM 探针设计器 + 安全闸门（核心，先做）
- 新增 `tools/llm_client.py`（极简 LLM 封装，失败 fail-open，usage 记账）
- 新增 `tools/design_probes_llm.py`（LLM 设计 + 铁则闸门 + 打回 1 次 + 脚本兜底）
- 抽出现有铁则校验为独立模块供闸门复用（不重复造）
- **验证方式（不跑 Unity）**：对一批**历史已入库关**用 LLM 重设计探针，人工评估设计质量（目标段选择是否合理、参数方向是否符合池子趋势、rationale 是否可信）。
- 回退：关 `project-state/llm_advisor.json` 的 enabled，恢复走现有 design_probes。

### Step 2：探针回测记账
- `probe_hitrate.json` 每轮回填；接入 auto_loop 收尾。
- 验证：跑 1 关 1 轮，确认每槽实际 WR 正确落表。

### Step 3：批次综合参谋
- 批次结束触发：简报 + 卡壳建议 + 规则空白。
- 验证：跑一批（或重放历史 round report），确认简报可读、卡壳触发正确。

### Step 4：优化循环启用
- 数据积累后按 §5.3 复盘，优化 LLM 输入/prompt。
- 是否加大 LLM 职权（如缺口分析也全权 LLM）由 Step 1-3 数据决定。

## 8. 可靠性与成本

- **fail-open**：LLM 调用失败/超时/解析失败 → 返回 None → 使用脚本方案兜底，主流程照跑。LLM 永不阻塞主流程（参考 08-14 白跑事故：附加环节失败绝不能中断主流程）。
- **规则唯一真源**：LLM 不写 rules.json、不改判定结果；探针要生效必须走既有 apply_probes + Warden + 轮次验证。
- **成本**：每关每轮 1 次探针设计调用 + 每批 1 次综合参谋；用现有 flash 模型，输入瘦身（结构化摘要），预估 ≤10k token/轮，相对 bot 400 局算力是零头。
- **可回退**：总开关一键关停；advisor 只追加；所有新文件不触碰现有 tools 主路径（新增旁路，不修改 design_probes.py 主体，降低回归风险）。

## 9. 职责边界

**三层架构**：确定性执行内核（批跑/入库/判定）+ LLM 探针设计核心 + 人最终裁定。

探针设计由 LLM 在候选目录内选择；规则负责安全闸门，真实批跑数据验证结果，用户负责最终裁定。

可核验边界：
- "探针是 AI 设计的吗？" → 是。LLM 读分层数据（verified+趋势）设计目标段和参数，规则只校验违规，不要求与脚本一致。
- "怎么证明 AI 设计得好？" → probe_hitrate 回测表：LLM 探针的实际命中率，且命中率低时我们优化 LLM 本身而不是回退脚本。
- "AI 会乱来吗？" → 铁则闸门兜底（5槽/sd跨度/ratios/非重复），打回 1 次，仍不行脚本兜底，主流程永不中断。

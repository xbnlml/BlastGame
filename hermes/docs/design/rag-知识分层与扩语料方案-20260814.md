# BlastGame 知识分层：什么进 RAG、什么留 skill/memory（分析+落地方案）

> **历史方案，已被当前实现取代。** 当前语料、chunk 数、模型 revision、构建哈希和严格评估只认 `../../rag/README.md`、`../../rag/index/build_manifest.json` 与 `../../rag/index/evaluation.json`。下文的目录与容量数字仅记录 2026-08-14 的规划状态，不是现行操作指令。

> 结论先行：**skill references 的 96 个"带日期的事故复盘/案例"文件（512KB）适合进 RAG；23 个"无日期的现行规则"文件（114KB）必须留 skill。MEMORY.md 接近满不是靠 RAG 解决的，但把其中的历史叙事拆到 RAG 语料能释放空间。成败关键不在"放进去"，而在"触发机制"——RAG 不会自动查，必须先在 .hermes.md/SKILL.md 里埋症状→查询路由表。**

## 一、判据：什么进 RAG vs 什么留 skill/memory

### 进 RAG 的四条判据（同时满足才放）
1. **体量大**：文档/知识块总规模超过"每次加载"的成本线（>100KB 就值得考虑）。
2. **按需查询**：只有出现特定场景才需要（排查某症状、回顾某机制），不是每次动手都要。
3. **语义查询**：用户/agent 用自然语言描述问题就能定位（"为什么白档""胜率怎么算"），而非精确命令/路径。
4. **不太常触发**：低频（一天不碰几次）。高频的放这里反而每次多一轮工具调用。

### 必须留 skill/memory 的四条判据（任一满足就留）
1. **必须每次都记得**（否则就出事）：安全铁则、不可逆操作闸门、用户禁令。遗忘的代价是事故（如 08-14 误写 15 关）。
2. **高频触发**：每次动手都要过一遍的工具清单、命令映射。
3. **时效精确**：当前标准/目标值/参数（过期就是错的——RAG 命中旧 chunk 反而误导）。
4. **是"行动指令"而非"知识"**：怎么写 asset、怎么调工具——命令必须精确且当前，历史版本害死人。

### RAG 的本质局限（决定边界）
- **RAG 是"主动查询"架构**：agent 不调用 `rag_query.py`，语料等于不存在。Hermes 当前没有自动 RAG 钩子，`.hermes.md` 里登记的也只是"查文档 → 手动跑 rag_query.py"。
- 因此**"必须记得"的绝不能放 RAG**。放进去 = 降级成"运气好才查到"。skill 的 INDEX.md 自己就承认了失败模式："有记录但没被触发"（84 个 reference 太多 → 检索失效）。
- **RAG 返回的是"证据/参考"不是"权威"**：语料含过期内容（如判定标准 15→10pp 的旧版本），agent 必须把 RAG 当"当年怎么试的"而不是"现在该怎么做"。

## 三、落地方式（三步走，改造成本很低）

现有 build_index 已经支持 `RAG_CORPUS_SUBDIRS` 环境变量，加语料目录零代码改动。推荐**单索引扩展 + domain 字段**起步，**必要时再拆双索引**。

### Step 1：建 ops 语料目录（快照式，不直接索引 skill 目录）
- 当时建议新建 `<BLASTGAME_REPO>/Doc/Ops/`；现行语料已经收口到项目内 `rag/data/corpus/Ops/`。
- 写一个 `scripts/sync_ops_corpus.py`：从 skill references 把 96 个日期文件**拷贝**进 Doc/Ops/（顺带做两件事）：
  1. 给已被新标准取代的旧文件**头部加一行** `> ⚠️ 已被 <新文件/新标准> 取代（日期），仅供历史参考`——让 chunk 文本自带过期警示，RAG 命中时 agent 能看到。
  2. 跳过 INDEX.md、SKILL.md、个人内容。
- 用拷贝而非软链/skill 目录直索引的原因：语料自包含、不随 skill 重构漂移、一拷就走、可独立清理。
- 拆分 `tool-fixes.md`：案例节 → Ops/，现行用法节留 skill。

### Step 2：重建索引 + 加 domain 字段（build_index 小改造）
- `rag/build_index.py` 的 metadata record 增加 `"domain"` 字段（按顶层子目录推导：MainGame/Bot/Tools→design，Ops→ops），改动约 10 行。
- 当时预计扩展后约 1450 chunks；现行构建以 manifest 记录的 1205 chunks 为准。
- `rag_query.py` 可选加 `--domain ops` 过滤参数（`_load_metadata` 已读全量，加个 filter 即可），方便按域检索。

### Step 3：评估（沿用现成 eval，扩 QA 集）
- 新建 `rag/data/golden_qa_ops.json`：20-30 条 ops 域 QA，`expected_source` 指向 Ops/ 文件名（如"白档怎么修"→ `Ops/leveldb-import-white-tier-20260813.md`，"同配置胜率差很多查什么"→ `Ops/optimizer-vs-bot-neutral-tier-rootcause-20260812.md`）。
- 当时规划单独 Ops QA；现行统一严格 source-only 评估及真实指标见 `rag/index/evaluation.json`。
- **回归验证**：同时跑原 49 条 design QA，确认把 Ops 混进同一索引后 design recall@1 不掉（若掉 >3pp，说明跨域污染 → 切双索引方案）。
- **双索引兜底方案**：若回归掉点，建第二个 index（ops 独立 faiss+metadata），`rag_query.py` 加 `--domain design|ops|all` 选索引。改造成本 ≈ 半天，两个索引各有独立 golden QA 和参数（ops 复盘文可试更大 chunk）。

### Step 4（最关键）：埋触发路由——RAG 不会自动查
- `.hermes.md`（每次自动加载）+ SKILL.md 加一张**症状→RAG 查询**路由表（10 行内）：
  ```
  # 查历史教训/案例（先 RAG 再动手）：
  为什么白档/红关 → python rag_query.py "白档 原因" --hybrid
  胜率不一致/同配置差很多 → python rag_query.py "同配置 胜率 不一致" --hybrid
  变慢/超时/unity 冲突 → python rag_query.py "批跑 变慢 原因" --hybrid
  某关为什么过不去 → python rag_query.py "L<关号> 探针 穷尽" --hybrid
  ```
- **触发铁则写入 MEMORY.md 一行**："排查症状类问题（白/红/不一致/变慢/关卡卡死）第一反应 `rag_query.py '症状' --hybrid` 查 Ops 历史，再动手"。这条必须进 memory，因为它是"必须记得"级。

## 四、边界：什么绝对不能放 RAG

1. **安全/不可逆操作闸门**：git 全禁、不写 BlastGame 项目目录、改关卡/入库必须用户确认、禁碰 Unity 核心文件（.meta/Library/manifest）。这些是 MEMORY.md + .hermes.md 的职责。
2. **每次动手必过的工具清单**：工具优先铁则、tools/README.md 命令映射、"禁止手写临时脚本"。放 RAG 等于复刻"有记录没被触发"事故。
3. **当前标准/目标值**：目标胜率定稿（80/80/60/45/45…）、判定标准（dev≤10 全绿）、局数标准（200/400）、rules.json。真源=项目文件 + MEMORY，RAG 里只有旧版会误导。
4. **数据可靠性硬约束**：phase1/2 不能直接入库、filter_verified、时间防线、dedup 按配置不按档位、reimport 后必须回读 DB。每条都是"忘了就出事"，必须每次可见。
5. **用户工作流偏好**：展示→确认→执行、用户裁定权、数据展示格式。这是与用户的契约，不是可检索知识。
6. **有副作用/时效敏感的精确指令**：write_ddc / gen_payload / reimport 的确切用法（08-14 事故就是手写 payload 误传 50 关）。命令真源留 tools/README + skill。
7. **个人/隐私内容**：叙事、同事可能看到的对话内容不入语料。

## 五、MEMORY.md 96% 满的处理（RAG 的间接作用）

MEMORY.md 33.7KB/147 条，**大量条目是同一主题跨日期重复**（探针设计铁则出现 5+ 次、局数标准 4 次、判定标准 3 次、bot400 一致性 3 次）。处理：
1. **压缩合并**：同一主题合并成一条"现行结论 + 日期"，预计 147 条 → 70 条以内，降到 ~20KB。合并时把各日期版本的**叙事细节**（证据链、数字、时间线）挪进 Doc/Ops/ 语料（或 references），MEMORY 只留一行"详见 <文件>"。
2. **去重**：凡 skill references 已详述的（如 l57 案例、bot400 审计），MEMORY 只留一行指针。
3. 目标：MEMORY 降到 <20KB（60% 以下），给未来 2-3 个月留空间。**压缩后的 MEMORY 是"现行真源"，旧版本进 RAG/归档，不删。**

## 七、预期收益与验证指标

- skill references 896KB→~114KB（92% 体量外移到 RAG，且不留空壳——留的是真正每次要用的）；SKILL.md 166KB 也可顺带瘦身（其大量行已在 references，可把 08-06 前的叙事段落外移）。
- 当时估计语料会从 928 增至约 1450 chunks；该估算已被当前 1205-chunk manifest 取代。
- **成败指标 = 触发率**：一周内统计 rag_query.py 被调用的场景是否覆盖"症状类问题"（白/红/不一致/变慢/卡死）。触发路由表在 .hermes.md，每次会话自动可见——这是本方案唯一真正要守住的点。
- 若 2 周后 ops 语料命中率低（<50% 症状场景先查了 RAG），回滚方案：把最高频的 10 个案例摘要写回 SKILL.md，RAG 只留长尾。

# BlastGame 设计决策文档（Design Decisions）— 结构骨架

> **文档用途**：技术面试自述弹药库。每个决策都能回答四连问：
> **为什么这样设计 / 对比过什么方案 / 代价是什么 / 边界在哪（真实项目证据）**。
> 写作原则：所有结论配量化数字与事故/边界案例，宁肯暴露弱点也不说空话。

## 第 0 章 30 秒版：核心数字速查表

面试开场 30 秒要能报出的数字，全部来自真实代码/记忆，不许含糊：

| 数字 | 含义 | 一句话解释 |
|---|---|---|
| 200 局 / 400 局 | 探针贝叶斯提前停 / 验证 | phase1/2 数据必须先 bot 400 局验证才能入库 |

## 第 1 章 系统全景（一章讲清"这是什么"）

- **一句话目标**：把"关卡难度"从人工经验变成可测量、可自动调优、可验证的闭环（Unity 游戏 + Python 工具链 + Hermes Agent 编排）。
- **架构图**：Planner（设计探针）→ Unity batch 模拟（产出局数据）→ Warden（安全/铁则检查）→ Judge（三态判定）→ Curator（入库/归档），两个存储面：关卡数据库（board.md 单一事实源）与 asset 配置面（probe_configs.json ↔ Unity asset 同步）。
- **数据流图**：每轮数据从生成、判定到入库的生命周期，标出 4 个"关卡点"（Warden 检查 / filter_verified / 时间防线 / 指纹校验）。
- **术语表**：档位、WR%（胜率）、目标（targets）、gap、接近带、相位、数据源分级、入库、回归。**面试中术语一致 = 项目真实感**。

## 第 2 章 核心决策（每个决策一章，统一 ADR 六段式模板）

> 每章严格按模板写，**六段缺一不可**。模板见第 3 章。

### D1 多 agent 编排：四个角色（Planner/Warden/Judge/Curator）而非一个单体循环
- 背景：单脚本循环跑通后失控——判定口径漂移、安全违规、阶段顺序异常（有 warden memory 事故记录为证）。
- 方案对比：单体循环 / 框架（LangGraph 等）/ 自研四角色流水线。
- 为什么：**最小自治 + 强护栏**——Planner 只负责"出探针"，Warden 独立拦截危险操作（git checkout/rm -rf/改 .meta 等铁则），Judge 独立做判定，Curator 独立入库；角色隔离 = 权限隔离 = 失败隔离。
- 代价：编排复杂度、上下文切分（每个 agent 只见局部）、角色漂移需 memory 对齐。

### D2 贝叶斯提前停：探针 200 局 / 验证 400 局怎么定出来的
- 背景：Unity batch 模拟一局成本高，全量跑满样本量吞吐不可接受；提前停要控制误判率。
- 方案对比：固定全量样本 / SPRT 序贯检验 / 贝叶斯提前停。
- 为什么：贝叶斯把"先验 + 已观测局数"合成停止判据，早停集中在"明显好/明显差"的探针上，模糊区继续跑；200 局是早停上限，400 局是入库验证的确认门槛（双重闸门：先停省成本、后验保质量）。
- 代价：统计尾巴——早停仍有假合格/假不合格概率，所以**验证 400 局不可省**；阈值需对模拟环境标定。

### D3 数据可靠性三件套：时间防线 + 四级数据分级 + asset 指纹
- 背景：逻辑/口径变更后旧批次数据"看起来还能用"——静默污染摧毁了对数据的信任（发生过 reimport 事故，board 留有备份痕迹）。
- 方案对比：写迁移脚本修旧数据 / 人工甄别 / **版本时间线直接作废**。
- 为什么：
  - 时间防线（LOGIC_VERSION_SINCE）：旧逻辑产出的批次**整批作废、永不复用**，比"修数据"便宜且零歧义；解析失败回退 1970（不拦截）= fail-open 设计要写明。
  - 四级分级：bot/summary/phase0 同级可信；phase1/2 带生成器偏置，永远降级。
  - asset 指纹：probe_configs.json ↔ Unity asset 双写不同步会静默覆盖，指纹校验抓"配置漂移"。
- 代价：schema 变更锁死（改逻辑=作废数据）、重跑成本、规则本身需维护。

### D4 相位制数据：生产候选与验证数据分离（phase1/2 永不直接入库）
- 背景：扫描型探针（广撒网）和定向型探针（精确调）产出的数据可信度不同，混在一起入库导致质量倒灌。
- 方案对比：统一入库按量打分 / 按相位分级+验证门槛。
- 为什么：phase0 先验（人工/经验）、phase1 扫描（多样性探索）、phase2 定向（缺口收敛）、phase3 回归（防改关卡引入回归）——**生成目的决定数据语义**；phase1/2 数据任何情况下不能直接用于入库决策，必须 bot 400 局验证（filter_verified 铁则）。
- 代价：管线延迟（验证多一轮）、相位簿记成本、与 6 轮上限的耦合。

### D5 探针缺口驱动设计：从目标胜率反推，而不是从手感设计
- 背景：150 关靠人手调参不可扩展；"设计者觉得难"不等于"玩家测出来难"。
- 方案对比：人工经验试错 / 规则模板 / **缺口驱动**：目标 WR → 反推参数 → 池子候选 → 自设计探针。
- 为什么：把"难度"这个主观词翻译成可测量的 gap（实际 WR vs 目标 WR 的偏差），设计循环有了可优化信号；目标偏差 15pp 硬规则保证入库关卡不偏离产品意图。
- 代价：目标语义本身是产品决策（目标错了系统会高效地错）；gap 信号依赖数据可靠性（所以 D3/D4 是它的地基）。

### D6 判定语义：三态判定 + 分档阈值 + 偏差分级
- 背景：早期 pass/fail 判定把"差一点"的批次要么当废数据扔掉、要么当合格入库，两者都亏；单一固定 gap 阈值在低胜率段失真。
- 方案对比：二态 / 三态；固定阈值 / 按较高档 WR 分档阈值（≥70% 档 gap≥20、50-70% 档 ≥15、30-50% 档 ≥10、<30% 档 ≥6）。
- 为什么：三态让"接近带"成为数据归宿（可入库但标记），不浪费已跑局数也不污染合格线；分档阈值承认"低基数下绝对 gap 无意义"；目标偏差 5/10/15 绿黄红分级，红=硬性违规。
- 边界与演进（重点写）：容差由**真实边界案例裁定**——L176 差 0.2pp、L152 差 0.01pp 触发 tolerance_pp=2 / near_tolerance_pp=1；判定用精确值（summary CSV 4 位小数）展示才四舍五入；删过"偏离≤2pp 直接合格"豁免——**判定标准是活的，每个修订都有案例背书**。

### D7（可选）人的边界：自动化到哪一步为止
- 背景：系统能自动判定，但"差 0.2pp 算不算合格"是产品问题不是数学问题。
- 方案对比：全自动硬规则 / 用户仲裁兜底。
- 为什么：边界案例（L176/L152）走用户裁定并固化为规则；手动挑配置记录保留人工干预通道。
- 代价：人工延迟进循环；但换来的是判定标准的可信度（面试金句：**知道哪些决策不该自动化，是 agent 应用的核心能力**）。

### D8（可选）状态一致性与可恢复性：单一事实源 + 备份纪律
- 背景：board.md 是关卡数据库的单一事实源，改关卡/reimport 是高危操作。
- 方案对比：数据库 / markdown 单一事实源 + 变更前备份。
- 为什么：board 每行一关、状态机清晰（✅入库/🟡待调优/🔴需改关卡）；所有破坏性操作前自动备份（board_before_reimport_* 即为证据）。
- 代价：无并发事务、规模上限；诚实写出"这证明了项目是真实迭代出来的，不是演示工程"。

## 第 3 章 每个决策的写作模板（ADR 六段式）

每章固定六段，直接回答面试四连问：

1. **背景与问题**：当时在跑什么、痛在哪（附一个真实事故/数字）。
2. **候选方案**：≥2 个认真考虑过的方案 + 为什么否决（否决理由比选择理由更显深度）。
3. **决策与理由**：选了哪个、量化依据（阈值怎么来的、样本量怎么定的）。
4. **代价与边界**：主动承认失去/妥协了什么——**这是区分真项目与包装项目的关键段**。
5. **演进与教训**：后来被哪些案例打脸/修订（每个规则改动都要有案例编号，如 L176/L152）。
6. **一句话答案**：30 秒能讲完的版本，面试现场直接背。

## 第 4 章 诚实目录：失败与未解问题（真项目身份证）

- **事故时间线**：reimport 事故、判定标准反复修订（7-31 分档 → 8-05 容差 → 删豁免）、阶段顺序异常记录（连续多轮 phase 全 1）、探针被 Warden 打回。
- **已知弱点**：提前停的统计尾巴、目标语义依赖产品判断、规则基数增长（判定/容差/硬性违规清单越来越长）、单机串行吞吐上限。
- **如果重来会怎么做**：1-2 条真实的"早知道"（如：时间防线应该第一天就上；判定阈值应该在 schema 里而不是在记忆里）。
- 这一章的价值：**面试官问"项目有什么不足"时，主动交底比被逼问出来强十倍**。

## 第 5 章 面试问答弹药库

- 高频问题表：问题 → 一句话答案 → 指向第 2 章哪一节深挖。
  - "为什么四个 agent？" → D1
  - "200/400 局怎么定的？" → D2
  - "数据可信度怎么保证？" → D3+D4
  - "判定阈值为什么分档？" → D6
  - "AI 在这里面到底干了什么？" → D5（缺口驱动+判定语义是 AI 价值核心）
  - "如果用户目标设置错了会怎样？" → D5 代价 + 偏差分级
  - "项目最大的坑是什么？" → 第 4 章
- **反例防御**：被 challenge（"这不就是调参工具吗"）时的三段回应：可测量化 → 自动化闭环 → 质量护栏，每段一个数字。

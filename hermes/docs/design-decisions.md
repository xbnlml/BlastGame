# BlastGame 设计决策

这个文档记录项目里比较重要的设计决策：当时面对什么问题、对比过哪些方案、最后选了什么、代价和边界在哪、后来有没有被案例打脸修订。原则是结论配数字和真实案例，不写空话。

## 核心数字速查

| 数字 | 含义 | 说明 |
|---|---|---|
| 默认 400 局 | CLI 默认模拟预算 | 可通过参数调整；第 1–5 轮可早停，第 6 轮跑满配置值 |
| 5 / 10pp | 目标偏差分层 | ≤5pp 可接受；5–10pp 接近并继续调优；≥10pp 非绿 |
| 三态判定 | 合格 / 接近 / 不合格 | 只有合格进入待确认入库；接近继续下一轮 |
| 4 相位 | phase0 先验 / 1 扫描 / 2 定向 / 3 回归 | phase1/2 任何情况下不能直接入库 |
| 2 层数据 | bot / summary / phase0 可用于判定；phase1/2 只作探索参考 | `filter_verified` 控制判定入口 |
| 6 轮上限 | 不合格→round+1，6 轮仍不合格→改关卡 | 防止死循环空转 |
| 时间防线 | LOGIC_VERSION_SINCE=2026-08-13T14:36 | 该时刻前批次按旧逻辑产出，整批作废永不复用 |
| 150 关 | L51-200 批次规模 | 批量、多档位、多难度 |

## 系统全景

- **一句话目标**：把"关卡难度"从人工经验变成可测量、可调优、可验证的闭环（Unity 游戏 + Python 工具链 + Hermes Agent 编排）。
- **架构**：Planner（选择探针）→ Warden（批前闸门）→ Unity batch（产出实测）→ 数据池刷新 → Judge（三态判定）→ Curator（只做观察和复盘）。入库不属于任何自动角色：人确认后才同步 asset、Excel、board 和 LevelDatabase。
- **数据流**：每轮数据从生成、判定到入库的生命周期，中间有 4 个关卡点（Warden 检查 / filter_verified / 时间防线 / 指纹校验）。
- **术语**：档位、WR%（胜率）、目标（targets）、gap、接近带、相位、数据源分级、入库、回归。

---

## D1 职责分离：LLM 只选择探针，确定性模块掌握闸门

- **背景**：单脚本循环跑通后失控——判定口径漂移、安全违规、阶段顺序异常（有 warden memory 事故记录为证）。
- **方案对比**：单体循环 / 通用 agent 框架 / 受限 LLM 选择器 + 确定性执行链。
- **决策**：Planner 只在候选目录中选择 5 个 candidate_id；Warden、Runner、Judge 保持确定性并 fail-closed；Curator 只记录观察，不写规则或入库数据。模型失败时脚本 fallback，主流程不依赖模型可用性。
- **代价**：需要维护候选 schema、决策 provenance 和 fallback；换来的是 AI 影响范围可测、可回放。

## D2 贝叶斯提前停：默认预算下按证据提前结束

- **背景**：Unity batch 模拟一局成本高，全量跑满样本量吞吐不可接受；提前停要控制误判率。
- **方案对比**：固定全量样本 / SPRT 序贯检验 / 贝叶斯提前停。
- **决策**：每轮默认配置 400 局，但 `--games/--probe-games` 可调整；第 1–5 轮启用 adaptive-stop，并设置 min-runs=60；第 6 轮关闭早停，跑满配置的 `--games`。关卡提前合格时停在待确认入库，不自动补跑验证轮。
- **代价**：早停结果仍有统计尾巴；阈值需要用模拟环境标定，入库记录必须保留实际局数和来源。

## D3 数据可靠性三件套：时间防线 + 数据分层 + asset 指纹

- **背景**：逻辑/口径变更后旧批次数据"看起来还能用"——静默污染摧毁了对数据的信任（发生过 reimport 事故，board 留有备份痕迹）。
- **方案对比**：写迁移脚本修旧数据 / 人工甄别 / 版本时间线直接作废。
- **决策**：
  - 时间防线（LOGIC_VERSION_SINCE）：旧逻辑产出的批次整批作废；同一关卡牌面未变时，历史有效批次继续累积复用。有 asset 快照时比较 level signature，无快照时比较批次时间与 asset 修改时间。
  - 数据分层：bot/summary/phase0 可进入判定池；phase1/2 带探索偏置，只用于趋势和候选设计。
  - asset 指纹：probe_configs.json ↔ Unity asset 双写不同步会静默覆盖，指纹校验抓"配置漂移"。
- **代价**：schema 变更锁死（改逻辑=作废数据）、重跑成本、规则本身需维护。

## D4 相位制数据：生产候选与验证数据分离（phase1/2 永不直接入库）

- **背景**：扫描型探针（广撒网）和定向型探针（精确调）产出的数据可信度不同，混在一起入库导致质量倒灌。
- **方案对比**：统一入库按量打分 / 按相位分级+验证门槛。
- **决策**：phase0 先验（人工/经验）、phase1 扫描（多样性探索）、phase2 定向（缺口收敛）、phase3 回归（防改关卡引入回归）——生成目的决定数据语义；phase1/2 不能直接用于入库决策，必须经过真实 bot 运行并转成 bot/summary/phase0 可靠来源（`filter_verified` 铁则）。
- **代价**：管线延迟（验证多一轮）、相位簿记成本、与 6 轮上限的耦合。

## D5 探针缺口驱动设计：从目标胜率反推，而不是从手感设计

- **背景**：150 关靠人手调参不可扩展；"设计者觉得难"不等于"玩家测出来难"。
- **方案对比**：人工经验试错 / 规则模板 / 缺口驱动：目标 WR → 反推参数 → 池子候选 → 自设计探针。
- **决策**：把"难度"翻译成可测量的 WR gap 和目标偏差；目标偏差严格小于 10pp 才保持数据库绿色，接近态继续调优，不直接入库。
- **代价**：目标语义本身是产品决策（目标错了系统会高效地错）；gap 信号依赖数据可靠性（所以 D3/D4 是它的地基）。

## D6 判定语义：三态判定 + 分档阈值 + 偏差分级

- **背景**：早期 pass/fail 判定把"差一点"的批次要么当废数据扔掉、要么当合格入库，两者都亏；单一固定 gap 阈值在低胜率段失真。
- **方案对比**：二态 / 三态；固定阈值 / 按较高档 WR 分档阈值（≥70% 档 gap≥20、50-70% 档 ≥15、30-50% 档 ≥10、<30% 档 ≥6）。
- **决策**：三态保留“差一点”的信息，但接近不会进入入库：它消耗一轮并继续调优；分档阈值承认低胜率段同样 pp gap 的体验差异更大。目标偏差 ≤5pp 可接受、5–10pp 接近、≥10pp 非绿。
- **边界与演进**：容差由真实边界案例裁定——L176 差 0.2pp、L152 差 0.01pp 触发 tolerance_pp=2 / near_tolerance_pp=1；判定用精确值（summary CSV 4 位小数）展示才四舍五入；删过"偏离≤2pp 直接合格"豁免——判定标准是活的，每个修订都有案例背书。

## D7 人的边界：自动化到哪一步为止

- **背景**：系统能自动判定，但"差 0.2pp 算不算合格"是产品问题不是数学问题。
- **方案对比**：全自动硬规则 / 用户仲裁兜底。
- **决策**：边界案例（L176/L152）走用户裁定并固化为规则；手动挑配置记录保留人工干预通道。
- **代价**：人工确认会增加等待时间，但能把产品裁决与确定性执行边界明确分开。

## D8 状态一致性与可恢复性：单一事实源 + 备份纪律

- **背景**：入库同时影响 asset、Excel、board 和 LevelDatabase，任何单一文件都不足以证明完成。
- **方案对比**：只维护 markdown 状态 / 写完即成功 / 四方写入后回读验证。
- **决策**：board 每行一关，只表达工作流状态；正式入库必须在同一次流程中完成 asset、Excel、board、LevelDatabase，并通过 asset↔DB 与配置记录核验。
- **代价**：无并发事务、规模上限。

## ADR 六段式模板（新决策按此写）

每章固定六段：

1. **背景与问题**：当时在跑什么、痛在哪（附一个真实事故/数字）。
2. **候选方案**：≥2 个认真考虑过的方案 + 为什么否决。
3. **决策与理由**：选了哪个、量化依据（阈值怎么来的、样本量怎么定的）。
4. **代价与边界**：主动承认失去/妥协了什么。
5. **演进与教训**：后来被哪些案例打脸/修订（每个规则改动都要有案例编号，如 L176/L152）。
6. **维护摘要**：本决策影响哪些模块、验证入口和后续修改边界。

## 失败与未解问题

- **事故时间线**：reimport 事故、判定标准反复修订（7-31 分档 → 8-05 容差 → 删豁免）、阶段顺序异常记录（连续多轮 phase 全 1）、探针被 Warden 打回。
- **已知弱点**：提前停的统计尾巴、目标语义依赖产品判断、规则基数增长（判定/容差/硬性违规清单越来越长）、单机串行吞吐上限。
- **如果重来会怎么做**：时间防线应该第一天就上；判定阈值应该在 schema 里而不是在记忆里。

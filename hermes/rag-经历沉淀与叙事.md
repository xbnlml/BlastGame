## 一、技术事实（做了什么，全真实）

### 项目一句话
为 BlastGame 游戏文档（MainGame/Bot/Tools，约 450KB、90+ 个 markdown）搭建本地语义检索工具：切块 → BGE 转向量 → FAISS 建索引 → 检索 → 评估，并加 BM25 混合检索。

### 技术栈（每项都有实际选择理由）
| 组件 | 选择 | 为什么 |
|------|------|--------|
| Embedding | BGE-small-zh-v1.5 | 中文好、轻量（512 维）、本地跑 |
| 向量库 | FAISS IndexFlatIP | 归一化后内积=余弦，中小语料够用 |
| 切块 | 标题切分 + 段落/句子兜底 | 有标题结构的 md，语义单元切分 |
| 检索 | 向量 + BM25 + RRF 融合 | 语义近义 + 精确术语互补 |
| 评估 | golden QA + recall@k + MRR | 用数据说话，不拍脑袋 |

### 关键数据（面试/讲述要背的）
- 语料：**450KB**，90+ 文档，建索引 **812 块**（chunk≤768）
- golden QA：**49 条**（20+ 模块 + 跨模块 + 负例）
- 纯向量：recall@1 **70%** →（扩 QA 后）**79.6%** →（调 chunk 后）**81.6%**，MRR **0.847**
- 混合检索（BM25+RRF）：recall@1 从 **70%→80%**（旧 10 条 QA 上）

### 消融实验结论（这是"用数据决策"的证据）
| chunk 上限 | recall@1 | 块数 | 结论 |
|-----------|----------|------|------|
| 128 | 69.4% | 3080 | 太小，语义被切碎 |
| 512 | 79.6% | 973 | 偏小 |
| **768** | **81.6%** | **812** | **最优（与1024同效果但更省）** |
| 1024 | 81.6% | 752 | 与768相同但块更大更费token |

### 过程中的关键决策
1. **数据源选型**：约束（AGENTS.md/规则）始终加载不进 RAG；知识（模块文档）进 RAG；结构化数据（board/池子）硬禁。
2. **切块是"语义上限"不是固定大小**：128/512/768 是"超过才二次切"的阈值。
3. **BGE query 指令**：query 加"为这个句子生成表示以用于检索相关文章："，passage 不加。
4. **归一化**：L2 归一化后内积=余弦，避免长向量天然得分高。
5. **时间防线**：内容 hash + 增量重建，防止过期数据（迁移自 BlastGame 调优的"时间防线"思想）。
6. **负例**：QA 里放了"云存档/PVP/广告"等不在语料的题，验证系统"不硬编"。

## 二、叙事话术（以后怎么讲、怎么写）

> "我给自己的游戏项目搭了一个本地 RAG 知识库，把 450KB 的模块文档变成可语义检索的引擎，recall@1 做到 81.6%，并且通过消融实验用数据选出了最优切块参数。"

### 版本 2：一段话（项目介绍版）
> "我给我的 BlastGame 项目（一个数据驱动调优系统）搭建了 RAG 知识库：把 90 多个游戏模块文档（450KB）切块、用 BGE 转向量、存进 FAISS，实现语义检索。核心不只是'跑通'，而是建立了一套评估体系——49 条 golden QA + recall@k + MRR，通过消融实验对比 5 种 chunk 大小，用数据选出了 768 这个最优值（81.6% 且最省 token）。还加了 BM25 混合检索解决精确术语召回。整个过程贯穿了我一贯的原则：数据驱动、可验证、不拍脑袋。"

### 版本 3：完整叙事（讲述/写博客用）
**背景**：我的 BlastGame 是一个数据驱动调优系统，一直在处理"结构化数据检索"（从池子找最优配置）。RAG 是把它延伸到"非结构化文本语义检索"的下一步。

**做了什么**：
1. **数据源选型**——用"约束 vs 知识"二分法：规则类（AGENTS.md）始终加载，叙述类（模块文档）进 RAG，结构化数据（board/池子）硬禁（避免 RAG 引入噪声和过期数据）。
2. **技术实现**——切块（标题+递归兜底）→ BGE 转向量（query 加指令）→ FAISS（归一化内积=余弦）→ 检索。
3. **评估体系**——49 条 golden QA（覆盖 20+ 模块 + 跨模块 + 负例），recall@k + MRR 量化。
4. **消融实验**——对比 128/256/512/768/1024 五种 chunk，用数据选 768。
5. **混合检索**——BM25 + RRF 融合，解决纯向量对精确术语召回不足。

**关键洞见**：
- 切块是"语义上限"不是固定大小——它决定"什么时候二次切"，不是"每块切多大"。
- "省 token"是检索后只注入命中片段的结果，不是切块的目的；切块解决的是检索精确度。
- 消融实验的价值是"控制变量归因"——只改一个参数，才能把效果变化归因于它。
- 小语料测试结论要谨慎——5 文件 10 题说 128 好，全语料 49 题说 768 好，要以更大样本为准。

**结果**：recall@1 81.6%、MRR 0.847，配置落地（chunk 768），系统可用。

### 常见追问 + 回答（你亲手做过，能扛住）
| 追问 | 回答 |
|------|------|
| 为什么不用 grep？ | 语义近义改写 grep 匹配不上；RAG 补语义检索能力，不吹生产收益 |
| 为什么选 BGE？ | 中文好、轻量；且 BGE 是不对称训练，query 要加指令 |
| 怎么证明 768 比 512 好？ | 49 条 QA 消融：512=79.6%、768=81.6%，1024 同效果但更费 token |
| 向量库为什么 FAISS？ | 中小语料、本地、够用；IndexFlatIP+归一化=余弦 |
| 过期数据怎么办？ | 内容 hash 检测，变化只重索引对应文件（迁移自调优的"时间防线"） |

### 写作/讲述原则（重要）
1. **讲过程不讲结论**：重点不是"我做了 RAG"，而是"我怎么用数据决策（消融）"。
2. **给具体数字**：450KB、812 块、49 条 QA、81.6%、0.847——数字让叙事可信。
3. **诚实**：语料小、混合检索提升有限都如实说，不吹"提升了 30%"（一查就穿）。
4. **突出独有**："结构化检索 → 语义检索"的成长弧线是别人没有的，BlastGame 是真项目不是玩具。

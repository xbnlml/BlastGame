# 判定标准与边界案例

## 合格判定标准（三态）2026-07-31 新分档 / 2026-08-05 更新
- 合格: gap ≥ 临界点（按较高档 WR 分档）
- 接近: gap 在接近带 [near, ok)，消耗一轮并继续调优，不进入入库
- 不合格: gap < 接近带下限 or 硬性违规
- 注：已删除"偏离≤2pp直接合格"豁免——接近带就是"差一点"的归宿

## 分档标准（2026-07-31）
| 较高档 WR | 合格gap | 接近gap |
|---|---|---|
| ≥70% | ≥20 | 15-20 |
| 50-70% | ≥15 | 10-15 |
| 30-50% | ≥10 | 7-10 |
| <30% | ≥6 | 4-6 |

Normal 查 T1→T3（按T1分档）、T3→T5（按T3分档）；Hard/SH 查相邻四档（按较高档分档）。

## 容差（2026-08-05 用户裁定）
- tolerance_pp=2：gap 在合格线下 2pp 内算合格（L176 差 0.2pp 案例）
- near_tolerance_pp=1：gap 在接近带下限 1pp 内算接近（L152 差 0.01pp 案例）
- 判定用精确值（summary CSV 4 位小数），展示才四舍五入

## 硬性违规清单
- 倒挂>1%, gap>40%(Hard/SH), WR<5%, <10%档>1个
- T3 锚点限制已从当前 Judge 判定中移除（2026-08-18 定稿）
- 注：gap<5% 已删除（新 <30% 段接近带下限为 4，gap 红线由分档覆盖）

## 目标偏差约束（2026-08-20 当前）
- rules.json target_deviation = {max:5, near:10, db_green_max:10, severity:hard}
- 每档 |WR-目标|≤5pp → 合格；5~10pp 且 DB 全绿 → 接近；>10pp → DB 非绿，不得接近
- check_judgment(combo, diff, targets) 传 targets 才启用


## 强化规则 (来自 MEMORY.md 提炼，2026-08-05 更新)

### 数据源优先级（2026-07-31 新语义 + 08-04 修正）
- bot / summary / phase0 几乎同级（_source_penalty 三者 rank 全 0，不再按局数分档）
- 同级冲突时新数据优先（created_at 更新者胜）
- phase2/phase1 仍罚且任何情况下不能直接入库

### filter_verified 铁则
- 入库决策必须先调 `filter_verified()`
- 通过: bot/summary/phase0 任意局数
- 拒绝: phase1/phase2 不能直接判定，必须先经真实 bot 运行转成可靠来源并记录实际局数
- phase1/phase2 数据任何情况下都不能直接用于入库决策

### 6轮上限
- `_rounds.json` 由 `judge_level.judge_with_rounds()` 管理
- 合格→重置并等待用户确认入库
- 接近/不合格→消耗有效轮次，最多 6 轮，随后等待用户确认改关卡
- 已入库关不挂轮次（2026-08-05 清理 L176/L153）

### 选最优档位质量分（2026-08-20）
- 任何档位 WR<5% 硬性过滤（_bucket 共用），L162 T5=0 案例
- 当前 `q = gap_distance + 0.25 × target_distance`，越低越好。
- gap_distance 使用实际/Excel目标的 log₂ 尝试次数档差距离，gap 过大不再奖励。
- Judge 规则独立负责合格/接近/不合格，q 只负责候选排序。
